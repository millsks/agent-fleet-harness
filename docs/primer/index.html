Building an agent fleet for the SDLC

A hands-on primer using Claude Code and the Claude Agent SDK. An agent is the model plus its harness: instructions, context, tools, permissions, checks and feedback. A fleet is a pipeline of narrow agents, each with its own harness, a gate before work moves on, and loops that heal failures and learn from them. Tap any station on the route to open its spec sheet.

Harness engineering: when an agent slips, fix the harness, not the model

The harness is everything except the model. Claude Code ships with a builder harness (system prompt, tools, the agent loop, compaction). Your team owns the outer harness: everything in the repo and CI that steers the agent before it acts (guides) and checks it afterward (sensors). Some parts are deterministic code; others are themselves model-judged. A strong fleet has all four quadrants filled.

The ratchet: turn each slip into a permanent fix

Pick a real failure. The habit is to prefer the most deterministic fix that works, and to add a test that would have caught it.

Inside one agent: gather, act, verify, repeat

Every agent in the fleet runs the same loop. It reads to build context, acts with a tool, checks the result, and goes around again until the work is verified or something stops it. Most fleet failures are this loop going wrong in a recognisable way. Pick a failure mode to see where it happens, how to spot it, and the harness fix.

GatherRead files, grep, run the Explore subagent, read spec.md and logs.
ActEdit, write, run commands, call MCP tools, delegate to subagents.
VerifyRun tests and lint, re-read the diff, compare against acceptance criteria.
ExitVerified, turn budget spent, or blocked and escalated.

Pick the smallest unit of coordination that works

Claude Code gives you five ways to put more than one agent on a job. They differ in who coordinates, whether agents can talk to each other, and whether a human has to be present. A CI fleet is mostly built from the last two rows, with subagents inside each run.

An agent is a Markdown file with a narrow job

Subagents live in .claude/agents/ (checked into the repo) or ~/.claude/agents/. Only name and description are required; the description is how the orchestrator decides when to delegate. Build one below and copy it into your repo.

Other useful fields: disallowedTools, permissionMode (plan for read-only planners), skills to preload, scoped hooks and mcpServers, memory, effort, and background: true. Claude Code silently ignores unknown fields, so typos fail quietly: check /agents after adding one.

Context engineering: spend the window on the task

Everything loaded at startup competes with the work itself, and long, cluttered context makes agents miss instructions. The rule is progressive disclosure: load a short map up front, and pull detail only when it is needed. Toggle the fixes below to see the effect on an example build agent.

Illustrative token counts for a typical repo, not measurements.

Long runs compact automatically; subagents can lower their threshold with autoCompactWindow, and omitClaudeMd: true skips CLAUDE.md for agents that don't need it. Claude Code warns at startup when custom subagent descriptions exceed 15,000 tokens.

Tool design: build tools for agents, not for developers

Agents are only as good as the tools they're given. An MCP server that mirrors your REST API one endpoint per tool usually performs badly: too many overlapping tools, huge outputs, and errors the agent can't act on. Design each tool around a task the agent actually performs.

Mirrors the API

list_users()        # returns all 40k users
list_orders()       # returns all orders
get_order(id)
run_sql(query)      # anything goes

→ Error 500

Shaped for the task

orders_search(customer_email, status=None,
              limit=20, detail="concise")
  # 20 rows, key fields, "12 more: pass page=2"
orders_get(order_id, detail="full")

→ No customer with email a@b.co. Try
  customers_find(name=...) first.

Fewer, consolidated tools

One tool per task, not per endpoint. Overlapping tools are the main reason agents call the wrong one.

Namespaced, plain names

Prefix by service or resource (orders_search, jira_issue_create) so names stay distinct across many servers.

Concise by default

Return the fields that matter, paginate and truncate with a hint about what's left, and offer a detailed mode.

Errors that teach

Say what was wrong and what to try next. The error message is a prompt the agent will act on.

Descriptions are prompts

Write the description as you would brief a new hire: when to use it, what the parameters mean, an example.

Evaluate tools like code

Run realistic tasks, read transcripts for wrong calls and wasted turns, and let an agent propose fixes to the descriptions.

The environment: make the repo easy for agents to work in

Agents fail on environments that humans have learned to work around: flaky setup, slow tests, tribal knowledge. Every item below cuts turns and false failures, and helps human engineers too.

Gates make "done" mean done

Prompts are guidance; hooks are enforcement. A hook is a command that runs at a lifecycle event and reads the event as JSON on stdin. Exit code 2 blocks: on PreToolUse it stops the tool call, and on Stop it refuses to let the agent finish and sends stderr back to it as work to do. That is how a build agent is forced to keep going until tests pass.

#!/usr/bin/env bash
# .claude/hooks/require-green.sh  (Stop hook)
input=$(cat)
# Avoid infinite loops: if we already pushed back once, let it stop
if [ "$(jq -r '.stop_hook_active' <<<"$input")" = "true" ]; then
  exit 0
fi
if ! out=$(make test 2>&1); then
  echo "Tests are failing. Fix them before finishing:" >&2
  echo "$out" | tail -n 40 >&2
  exit 2   # block the stop, feed stderr back to Claude
fi
exit 0
// .claude/settings.json
{
  "hooks": {
    "Stop": [{ "hooks": [{ "type": "command",
      "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/require-green.sh" }] }],
    "PreToolUse": [{ "matcher": "Bash", "hooks": [{ "type": "command",
      "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/no-force-push.sh" }] }]
  }
}

Orchestrating: events in, artifacts out

Two ways to wire the route. Start with GitHub Actions, where each label is a station and the repo is the shared state. Move to the Agent SDK when you need retries, custom state, or to run on your own infrastructure.

Self-healing: let agents fix red builds, with hard stop rules

A healer agent runs when CI fails. It reads the failed log, decides what kind of failure it is, and either fixes the root cause on the same branch or hands off. The hard part isn't the fix, it's stopping: without loop guards a healer can burn budget, weaken tests to make them pass, or fight another agent forever.

CI failsworkflow_run completes with failure
Classifycode bug, lint/type, flaky, infrastructure, unknown
Check breakersattempts, same error twice, cost, protected branch
Fix or hand offcommit [agent-heal], or file a quarantine issue
Escalatelabel needs-human with heal-report.md

Should the healer try again?

# .github/workflows/agent-heal.yml
name: agent-heal
on:
  workflow_run:
    workflows: ["CI"]
    types: [completed]
concurrency:
  group: heal-${{ github.event.workflow_run.head_branch }}
  cancel-in-progress: false
jobs:
  heal:
    if: >
      github.event.workflow_run.conclusion == 'failure' &&
      github.event.workflow_run.head_branch != 'main'
    runs-on: ubuntu-latest
    timeout-minutes: 30
    permissions:
      contents: write
      pull-requests: write
      issues: write
      actions: read
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.event.workflow_run.head_branch }}
          fetch-depth: 50
      - name: Circuit breaker and failure log
        id: cb
        env:
          GH_TOKEN: ${{ github.token }}
        run: |
          n=$(git log --since="24 hours ago" --grep='\[agent-heal\]' --oneline | wc -l)
          echo "attempts=$n" >> "$GITHUB_OUTPUT"
          gh run view ${{ github.event.workflow_run.id }} --log-failed | tail -n 400 > ci-failure.log
      - name: Heal
        if: steps.cb.outputs.attempts < 3
        uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          github_token: ${{ secrets.HEALER_APP_TOKEN }}
          prompt: |
            CI failed. Read ci-failure.log and find the root cause of the FIRST failure.
            Classify it as CODE, LINT, FLAKY, INFRA or UNKNOWN in heal-report.md.
            Only for CODE or LINT: fix it, run make test-fast, and commit with a
            message starting "[agent-heal]".
            Never skip, delete or loosen a test or assertion. Never edit CI config.
            If the error matches the previous heal attempt in git log, stop and say so.
          claude_args: "--max-turns 25 --model sonnet"
      - name: Escalate
        if: steps.cb.outputs.attempts >= 3
        env:
          GH_TOKEN: ${{ github.token }}
        run: |
          gh pr comment "${{ github.event.workflow_run.head_branch }}" \
            --body "Healer stopped after 3 attempts today. Needs a human."
          gh pr edit "${{ github.event.workflow_run.head_branch }}" --add-label needs-human

Pushes made with the default GITHUB_TOKEN don't trigger new workflow runs, so CI would never re-check the fix. Push with a GitHub App token instead, which is also why the attempt counter matters. Pair it with a PreToolUse hook that blocks edits under .github/ and to test files' assertions.

Self-learning: the fleet proposes changes to its own harness

Models don't learn between runs; the harness does. Learning means turning outcomes into reviewed, versioned changes to CLAUDE.md, agent prompts, skills, hooks and tests. A retrospective agent does the analysis, the eval suite checks the change didn't make things worse, and a human merges it.

Outcomesmerged PRs, rejected PRs, human fix-up commits, review comments, heal reports
Retro agentweekly: finds repeated slips and their cause
Harness PRat most three changes, each citing the PRs that prove it
Eval gatepass rate and cost must not get worse
Human mergesand deletes stale rules
---
name: retro
description: Weekly review of fleet outcomes. Proposes harness changes.
tools: Read, Grep, Glob, Write, Bash
model: opus
maxTurns: 40
memory: project
---

Review the last 7 days of agent work with `gh`:
- agent PRs that were closed unmerged, and why
- merged agent PRs that needed human fix-up commits
- review comments that repeat across PRs
- heal-report.md files that ended in UNKNOWN or escalation

Find patterns that happened at least twice. For each, propose the
most deterministic fix that would have prevented it, in this order:
test or lint rule > hook > skill > CLAUDE.md line > agent prompt.

Write proposals to harness-proposals.md. Each one cites the PRs
that show the problem. Propose at most three. Also list any
existing CLAUDE.md rule that nothing has needed in 30 days.

Guardrails for learning

  • Diffs, not drift. Every learned change is a commit to a file in version control, so it can be reviewed, blamed and reverted. Subagent memory is useful for an agent's own notes, but review those files too.
  • Evidence required. No rule without at least two incidents behind it.
  • Evals before merge. A harness change runs against the fixed task set; a drop in pass rate or a jump in cost blocks it.
  • Garbage collection. Rules accumulate. Delete ones that nothing triggers, so CLAUDE.md stays short.
  • Humans own the rules. The fleet proposes; people approve. Never let an agent merge changes to its own prompts or hooks.

Observe and evaluate the fleet like a production service

You can't improve a harness you can't measure. Export telemetry from every run, track a few numbers per station, and keep a fixed set of past tasks to replay whenever the harness changes.

Replay a fixed task set on every harness change

#!/usr/bin/env bash
# evals/run.sh: each task dir has base_commit, prompt.md, check.sh (hidden tests)
set -u
out=evals/results/$(git rev-parse --short HEAD); mkdir -p "$out"
for t in evals/tasks/*/; do
  id=$(basename "$t"); wt=$(mktemp -d)
  git worktree add -q --detach "$wt" "$(cat "$t/base_commit")"
  cp -r .claude CLAUDE.md "$wt"/          # the harness version under test
  ( cd "$wt" && claude -p "$(cat "$OLDPWD/$t/prompt.md")" --max-turns 30 \
      --output-format json > "$OLDPWD/$out/$id.json" )
  if ( cd "$wt" && bash "$OLDPWD/$t/check.sh" ); then r=pass; else r=fail; fi
  cost=$(jq -r '.total_cost_usd // "n/a"' "$out/$id.json")
  echo "$id $r $cost" | tee -a "$out/summary.txt"
  git worktree remove --force "$wt"
done
grep -c ' pass ' "$out/summary.txt"

Start with 20 to 30 real issues your team already solved, with their real fixes' tests as check.sh. Results vary run to run, so compare averages over two or three runs before accepting a change.

Ten rules that keep a fleet trustworthy

Separate the maker from the checker

The agent that wrote the code never writes its acceptance tests or reviews it. A fresh context with a different prompt catches what the author rationalised away.

Hand off files, not chat

Every station emits an artifact the next one reads: issue labels, spec.md with acceptance criteria, a branch, a test report, review comments. Artifacts are auditable and survive restarts.

One writer per file

Parallel agents get disjoint file sets or their own worktree. Merge conflicts between agents are the most common way fleets waste tokens.

Least privilege by role

Reviewers and planners are read-only. Builders get Edit and a scoped Bash allowlist. Only the release agent touches tags, and it never force-pushes.

Budget every run

Set maxTurns / --max-turns, job timeouts and concurrency limits. A runaway agent costs money, not just time.

Gates are code, not prompts

"Run the tests" in a prompt is a request. A Stop hook that exits 2 is a guarantee. Put lint, tests and secret scans in hooks and CI.

Humans at irreversible points

Approve specs for features, approve merges to main, approve releases. Let agents run freely in between, where everything is a branch you can delete.

Every slip tightens the harness

When an agent gets something wrong, ask which guide or sensor would have stopped it, add it, and add the case to the eval set.

Loops need exits

Every retry loop has an attempt cap, a cost cap and a no-progress check. When one trips, the agent escalates with a report instead of trying again.

Measure the fleet like a service

Log stream-json output, track pass rate per station, reopen rate, turns and cost per merged PR. Keep a small eval set of past issues to test prompt changes against.
